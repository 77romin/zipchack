# RAG 설계 제출 보충

실행 흐름·역할·장애 처리·도메인 설계 이유는 [주 설계문서](../RAG_파이프라인_설계.md)를 따른다. 여기서는 요구사항6장의 상세 설계 확인점을 보충한다.

## 컬렉션과 필드

| 컬렉션 | 내용 | 청크 규칙 |
| --- | --- | --- |
| zipchack_metadata | 항목의 공식 이름·코드·자치구·자료 한계 | 항목당1개 |
| zipchack_external | 위키 본문·공식 위치/인구 기반 문서 | 기본1000자/중복200자 |

두 컬렉션 공통 필드는 `item_id`, `document_id`, `kind`, `title`, `source_url`, `observed_at`, `chunk_index`, `chunk_size`, `chunk_overlap`, `fingerprint`다. 제공 시 `license`, `revision_id`, `attribution`을 추가한다. 컬렉션에는 embedding_model을 기록한다. ID는 항목·문서·유형 namespace와 청크순서의 SHA256이며 동일 문서를 다른 항목에 붙여도 덮어쓰지 않는다.

## 세 프롬프트

| 프롬프트 | 역할·입력 | 파싱 출력 |
| --- | --- | --- |
| P1 | 동네 자료 전문가, 질문·항목으로 검색어1~3개 | `{"queries":["검색어"]}` |
| P2 | 제목·요약 후보에서 관련 문서최대3개 선별 | `{"selected":[{"id":"후보ID","reason":"선택이유"}]}` |
| P3 | 검색된 번호·본문·종류·시점만으로 근거 답변 | `{"answer":"주장 [1]","abstained":false}` |

P1/P2의 실제 문자열은 `rag_prepare.py`, P3는 `rag_pipeline.py`에 포함된다. 질문·문서의 지시를 데이터로만 취급하고 임의 URL·근거 없는 가격/시간 추정을 금지한다. 후보ID·중복·길이·인용번호를 코드로 검증한다. P3의 형식 검증은 의미적 환각 방지와 동일하지 않다.

## 설정 이유와 관찰

1000자·200자 중복은 지역 문서의 문맥을 유지하면서 모델에 제공하는 길이를 제한하는 초기값이다. 실제 설정 비교는1000/200에서2청크,300/60에서5청크였다. 최적값을 찾아낸 실험은 아니며 청크 증가 자체를 품질 향상으로 해석하지 않는다.

Top-k4는 기본 후보 범위를 제한하는 초기값이고 fetch_k20에서 유사도 또는MMR로 선택한다. UI1~20/CLI에서 바꿀 수 있다. 공덕역 질문에서k1→4는 외부1→4청크로 바뀌고 MMR은 마포구 문서를 추가했다. 다른 문서가 늘어도 자치구의 특성을 특정 동네로 오인할 위험이 있다.

retrieve는 대상 항목 메타데이터를 항상 넣고 같은 항목 외부 결과를 합친 뒤 청크ID로 중복 제거해 번호를 매긴다. generate 후 실제 답변의 번호만 골라 문서 종류·ID·URL이 같은 인용을 묶는다. 검색 청크 수와 화면 인용 문서 수는 다를 수 있다.

두 컬렉션은 필수 식별 근거와 설명 근거를 구분하기 위해 선택했다. 조건 추출·가격/거리 계산을 LLM에서 분리한 이유는 숫자와 위치를 임의 생성하지 않게 하기 위해서다. 스냅샷 시점·법정동/행정동 차이·미조회·제외 행을 노출한다. 겪은 문제와 해결은 [README](../../README.md#만들면서-해결한-문제)에 정리했다.
