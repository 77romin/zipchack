# RAG 프로젝트 구현목표 정의서

- 작성일: 2026-10-21
- 현재 단계: 기획
- 도메인: 미정
- 기준 문서: [요구사항 참조](./RAG_프로젝트_요구사항_참조.md), [원본 요구사항 정의서](./AI코어프로젝트_2회차_요구사항정의서.pdf)
- 문서 성격: 원본 요구사항을 충족하기 위한 구현 목표와 프로젝트 자체 실험 계획. 구현·측정 완료 보고서가 아니다.

## 1. 프로젝트 목표

선택한 도메인의 항목 메타데이터와 외부 문서를 청킹·임베딩하여 Vector DB에 적재하고, 사용자 질문에 필요한 근거를 검색해 답변하는 RAG 서비스를 구현한다. LangGraph로 검색과 생성을 분리하고, 검색어 추출·후보 문서 선별·답변 생성의 세 프롬프트를 설계한다.

유사도 검색과 MMR 검색을 각각 구현하여 검색 결과, 답변 품질, 처리 속도를 비교한다. RAG 미사용 답변과도 비교해 RAG의 효과를 검증하고, 결과를 수치·표·도표로 정리한다. MMR이 반드시 품질을 개선한다고 가정하지 않고 측정 결과로 판단한다.

## 2. 요구사항과 구현 범위

| 구분 | 범위 | 기준 |
| --- | --- | --- |
| 필수 | 데이터 준비·색인, 문서 수집, 근거 검색·생성·표시, 채팅·탐색·특화 기능·안내 | F2001~F2012 |
| 선택하여 구현할 심화 | MMR 검색과 유사도 검색 비교 | F2014 |
| 선택하여 구현할 심화 | RAG 사용 전후 품질 비교·검증 | F2015 |
| 프로젝트 자체 확장 | 품질·속도의 정량 측정, 반복 실험, 수치·도표 작성 | 본 문서의 실험 계획 |
| 미정 | HTML·CSS·JavaScript 프론트엔드 직접 구현, 여러 종류의 외부 문서 출처 결합 | F2013, F2016 |

정량 지표·실험 규모·목표 응답 시간은 원본에서 지정한 수치와 프로젝트 자체 선택을 구분해 관리한다. 이 문서의 권장 실험 규모는 원본의 추가 필수 조건이 아니다.

## 3. 데이터 준비 및 색인 목표

### 3.1 도메인과 데이터 확보

- 이름과 속성을 가진 항목 메타데이터를 약 100건 이상 확보한다.
- 항목과 연결되는 외부 설명 문서의 확보 가능성을 확인한다.
- 데이터·문서 출처와 이용 조건을 기록한다.
- 근거 없이 답하면 틀리거나 위험해지는 대표 질문을 3개 이상 정의한다.
- 1일차 16시까지 도메인과 조건 충족 근거를 확정한다. 메타데이터를 확보하지 못하면 제공 영화 도메인 팩으로 전환한다.
- 위험한 판단이 가능한 도메인이라면 전문가 조언을 대신하지 않는다는 안내를 설계한다.

### 3.2 항목 메타데이터 컬렉션

- 항목 1건의 속성을 하나의 검색 텍스트로 구성한다.
- 텍스트를 임베딩하여 메타데이터 전용 컬렉션에 저장한다.
- 고정된 항목 식별자를 사용해 재색인 시 중복 저장을 방지한다.
- 로드 항목 수와 색인 청크 수를 확인할 수 있게 한다.

### 3.3 외부 문서 컬렉션

- 선별한 문서의 본문과 원문 출처를 수집한다.
- 본문을 청크로 나누고 임베딩하여 메타데이터와 별도 컬렉션에 저장한다.
- 청크 크기와 중복 길이는 설정에서 변경할 수 있게 한다.
- 문서 제목, 원문 출처, 관련 항목을 청크 메타데이터에 저장한다. 출처는 URL 또는 파일명·쪽으로 추적할 수 있게 한다.
- 청크 ID를 항목 ID·문서 ID·청크 순번 등으로 구성해 항목 간 덮어쓰기를 방지한다.
- 이미 수집·색인한 검색어는 다시 수집하지 않도록 캐시한다.

## 4. 세 프롬프트와 외부 문서 수집 목표

| 프롬프트 | 입력 | 역할 | 출력 목표 |
| --- | --- | --- | --- |
| 검색어 추출 | 선택 항목, 사용자 질문 | 도메인 전문가 역할로 외부 문서 검색어 도출 | JSON 등 파싱 가능한 형식 |
| 후보 문서 선별 | 질문, 항목, 검색 후보의 제목·요약 등 | 관련성이 높은 문서를 골라 불필요한 본문 수집 감소 | 후보 식별자가 포함된 구조화 결과로 설계 |
| 답변 생성 | 질문, 검색·병합한 근거와 근거 번호 | 검색 문서만 사용해 답변하고 주요 주장에 근거 표시 | 근거 번호를 포함한 답변, 근거 부족 시 확인 불가 안내 |

수집 흐름:

1. 사용자 질문과 선택 항목으로 검색어를 추출한다.
2. 외부 문서 출처에서 후보를 검색한다.
3. 후보 선별 프롬프트로 색인할 문서를 고른다.
4. 본문과 원문 출처를 수집한다.
5. 청킹·임베딩 후 외부 문서 컬렉션에 적재한다.

선택한 항목 자체를 다룬 문서는 반드시 검색 대상에 포함하고, 선별·길이 등 제외 규칙보다 우선하여 항상 색인한다. 외부 호출이 제한되는 환경에서는 원본이 허용한 제공 문서 묶음으로 수집 단계를 대체할 수 있다.

## 5. LangGraph RAG 파이프라인 목표

LangGraph는 필수 요구사항에 따라 `retrieve`와 `generate` 두 노드로 구성한다. 세 프롬프트를 각각 LangGraph 노드로 만들어야 한다는 의미는 아니다. 외부 문서 준비와 질의 시 검색·생성의 책임을 구분한다.

```text
[데이터 준비]
항목 메타데이터 → 항목별 텍스트 → 임베딩 → 메타데이터 컬렉션

[외부 문서 준비]
항목·질문 → 검색어 추출 → 외부 후보 검색 → 후보 선별
          → 본문·출처 수집 → 청킹·임베딩 → 외부 문서 컬렉션

[LangGraph 질의 처리]
START → retrieve → generate → END
           │           │
           │           └─ 검색된 문서만 사용, 주장별 근거 번호 부여
           └─ 선택 항목 메타데이터 포함 + 외부 문서 검색
              → 병합·중복 제거·근거 번호 구성

[화면 표시]
답변 + 실제 인용된 문서의 제목·원문 출처
```

### 검색 노드

- 선택한 항목의 메타데이터는 항상 근거에 포함한다.
- 질문과의 의미 유사도로 외부 문서 청크를 검색한다.
- 두 컬렉션의 결과를 병합하고 중복 청크를 제거한다.
- 근거에 항목 메타데이터와 외부 문서의 유형을 구분한다.
- Top-k를 설정으로 조정한다. 외부 청크 수와 메타데이터를 포함한 최종 근거 수를 명확히 기록한다.

### 생성 노드 및 근거 표시

- 검색된 문서만을 바탕으로 답변한다.
- 근거가 없거나 부족하면 추측하지 않고 확인되지 않는다고 응답한다.
- 주요 주장에 근거 번호를 붙인다.
- 화면에는 실제 인용된 근거 문서만 제목·원문 출처와 함께 표시한다.
- 인용된 근거가 하나도 없으면 그 사실을 안내한다.

## 6. 서비스 구현 목표

기술 파이프라인과 함께 다음 필수 사용자 기능을 구현한다.

| 기능 | 완료 조건 |
| --- | --- |
| 항목 선택·채팅 | 항목 선택 후 질문 가능, 항목별 대화 기록 분리·유지 |
| 자연어 조건 탐색 | 입력 조건에 맞는 항목만 선별·제시하고 선택 후 해당 항목 질문으로 연결 |
| 도메인 특화 기능 | 최소 1개 구현, 검색된 문서를 사용하고 결과에 근거 표시 |
| 상태·오류 안내 | 문서 수집·답변 생성 상태, 색인 없음·키 누락·검색 결과 없음 안내 |
| 위험 도메인 안내 | 해당 시 전문가 조언을 대신하지 않는다는 문구 표시 |

도메인과 특화 기능의 구체적인 내용은 기획 과정에서 확정한다.

## 7. 비교 실험 설계

### 7.1 비교 조건

| 조건 | 구성 | 비교 목적 |
| --- | --- | --- |
| A | RAG 미사용 LLM | 모델 자체 답변의 기준 성능 |
| B | RAG + 유사도 검색 | A 대비 검색 근거 제공 효과 |
| C | RAG + MMR 검색 | B 대비 근거 다양성 확보 효과 |

A에는 선택 항목의 식별 정보와 질문을 제공하고 검색 근거는 제공하지 않는다. B와 C는 동일한 메타데이터·외부 문서 스냅샷을 사용한다. 프롬프트는 공통 답변 원칙을 유지하되, A에는 존재하지 않는 근거 인용을 요구하지 않는다. 실제 조건별 프롬프트를 기록한다.

### 7.2 통제할 조건

- 같은 질문 세트, 모델 버전, 생성 파라미터, 출력 길이 제한을 사용한다.
- B와 C는 임베딩 모델, 청킹 설정, 검색 범위, 최종 근거 수, 병합·중복 제거 규칙을 동일하게 유지한다.
- 선택 항목 메타데이터는 B와 C 모두 동일하게 포함한다.
- MMR의 후보 수와 다양성 계수는 별도로 기록한다. 최종 근거 수와 후보 수를 혼동하지 않는다.
- 속도 비교에서는 동일 실행 환경·캐시 조건을 유지하고 호출 순서를 섞어 순서 효과를 줄인다.
- 대화 문맥의 영향을 통제하기 위해 평가 질문은 동일한 초기 대화 상태에서 실행한다.

### 7.3 질문 및 정답 기준

- 원본 F2015 기준으로 대표 질문은 최소 5개 이상 준비한다.
- 정량 비교의 안정성을 위해 프로젝트 자체 계획으로 20~30개 이상의 질문과 조건별 3회 이상 반복을 권장한다. 실제 규모는 비용·일정 검토 후 확정한다.
- 단일 사실, 여러 근거 종합, 조건 비교, 근거에 답이 없는 질문을 포함한다.
- 질문별로 정답 기준, 확인 출처, 답변 가능 여부, 필수 사실 요소를 사전에 작성한다.
- 답변 가능 여부는 고정된 평가 문서 집합을 기준으로 정한다.
- 설정 조정용 질문과 최종 평가용 질문을 구분한다. 최종 평가 결과를 보며 설정을 반복 최적화하지 않는다.

## 8. 정량 평가 지표

다음은 프로젝트 자체 평가안이다. 도메인 확정 후 판정 기준과 목표치를 고정하고 측정한다.

| 영역 | 지표 | 측정 정의 |
| --- | --- | --- |
| 답변 품질 | 사실 정확성 | 정답 기준과 일치하는 평가 대상 사실 요소 수 / 평가 대상 사실 요소 수 |
| 답변 품질 | 근거 일치율 | 인용 근거가 실제로 뒷받침하는 주장 수 / 인용이 있는 검증 대상 주장 수 |
| 답변 품질 | 근거 제시율 | 유효한 인용이 있는 검증 대상 주장 수 / 전체 검증 대상 주장 수 |
| 답변 품질 | 적절한 답변 유보율 | 답변 불가 질문에서 확인 불가를 밝히고 근거 없는 단정을 하지 않은 응답 수 / 답변 불가 질문 응답 수 |
| 답변 품질 | 답변 가능 질문 응답 성공률 | 답변 가능한 질문에 정답 기준을 충족한 응답 수 / 답변 가능 질문 응답 수 |
| 검색 품질 | 근거 적합도 | 질문에 관련 있다고 판정한 외부 청크 수 / 반환된 외부 청크 수 |
| 검색 다양성 | 청크 간 평균 유사도 | 반환 외부 청크 쌍의 임베딩 코사인 유사도 평균. 낮을수록 내용 분산이 크지만 관련성 지표와 함께 해석 |
| 검색 다양성 | 고유 문서 수 | 최종 근거에 포함된 서로 다른 외부 문서 수 |
| 속도 | 검색 시간 | 질의 임베딩·벡터 검색·MMR 선별·병합·중복 제거를 포함한 retrieve 노드 소요 시간 |
| 속도 | 생성 시간 | generate 노드 시작부터 전체 답변 완료까지의 시간 |
| 속도 | 전체 질의 응답 시간 | 입력 접수부터 답변·근거 구성 완료까지. 외부 수집 포함 여부를 반드시 표시 |
| 준비 비용 | 수집·색인 시간 | 외부 검색·선별·수집·청킹·임베딩·적재의 단계별 시간 |

분모가 0인 지표는 0점이나 100%로 임의 처리하지 않고 N/A로 기록한다. A의 근거 일치율과 검색 지표는 N/A이며, A의 검색 근거 제시율은 검색 근거가 없다는 실험 조건에 맞춰 해석한다. 사실 정확성에서 답변 누락을 숨기지 않도록 질문별 필수 사실 요소와 응답 성공률을 함께 보고한다.

사람이 사전 기준에 따라 판정하고, 가능하면 조건명을 가린 상태로 평가한다. LLM 평가를 보조로 사용한다면 평가 모델·프롬프트·사람의 확인 절차를 기록한다. 자동 평가 점수를 곧바로 사실 정확성으로 간주하지 않는다.

## 9. 속도 측정과 결과 기록

### 실행 상황 구분

1. 최초 처리: 외부 문서 검색·수집·색인이 필요한 상황의 전체 시간과 단계별 비용.
2. 준비 완료 질의: 문서가 이미 색인된 상황에서 A·B·C의 답변 품질과 응답 속도 비교.
3. 캐시 검증: 같은 검색어를 재요청했을 때 재수집이 발생하지 않는지 확인.

준비 완료 상태의 질의 비교와 최초 수집 비용을 섞어 검색 방식의 속도 차이로 해석하지 않는다. 실패·타임아웃은 제외해 숨기지 않고 별도 건수와 실패율로 기록한다.

### 결과 저장 필드

`experiment_id`, `question_id`, `item_id`, `condition`, `repeat`, 모델·프롬프트 버전, 데이터 스냅샷, 청킹 설정, 임베딩 모델, Top-k, MMR 후보 수·다양성 계수, 캐시 상태, 검색 청크 ID·문서 ID, 답변, 인용, 품질 판정, 단계별 시간, 오류 여부를 저장한다.

질문별 비교와 전체 집계를 모두 남긴다. 시간은 평균·중앙값·표준편차를 제시하고 충분한 표본이 있으면 p95도 제시한다. 반복 실행을 서로 다른 질문으로 세어 표본 수를 부풀리지 않는다. 개선폭은 퍼센트포인트와 상대 변화율을 구분한다.

## 10. 수치·도표 산출물

- A·B·C별 사실 정확성, 답변 유보율, 응답 성공률 비교표와 막대그래프.
- B·C별 근거 적합도, 근거 일치율, 고유 문서 수, 청크 간 평균 유사도 비교표.
- 조건별 응답 시간 분포 그래프와 검색·생성 시간 구성 그래프.
- 최초 수집·색인 시간과 준비 완료 질의 시간을 구분한 표.
- 같은 질문에 대한 A·B·C 답변·근거·평가를 나란히 보여주는 사례표.
- 성공 사례뿐 아니라 오답, 불필요한 답변 유보, 무관한 근거, MMR로 성능이 낮아진 사례 분석.

각 도표에는 질문 수·실행 수·단위·실험 조건을 표시한다. 표본이 작으면 결과의 적용 범위를 해당 질문 세트로 한정한다.

## 11. 비기능 목표

- API 키는 환경변수로 관리하고 소스·제출물에 포함하지 않는다.
- 화면에 API 키·프롬프트 전문·오류 추적 정보를 노출하지 않는다. 파이프라인 설계문서의 프롬프트 설명과 사용자 화면 노출은 구분한다.
- 데이터 준비·수집·색인·검색·생성·UI 책임을 모듈로 분리한다.
- 외부 API 재시도·호출 간격·필수 식별 정보 및 출처 이용 조건을 준수한다.
- 응답 시간의 원본 기준은 사용에 지장이 없어야 한다는 것이다. 구체적인 목표 초는 기획 후 확정한다.
