> **내 맘에 착, 내 삶에 착.**
> 예산부터 출근길까지, 나에게 착 맞는 집과 동네.

- 작성일: 2026-10-21
- 버전: v0.1 / 기획안
- 상태: 도메인 후보 구체화. 데이터 확보·API 실호출·구현·성능 검증은 미완료.
- 기준: [원본 요구사항 정의서](./AI코어프로젝트_2회차_요구사항정의서.pdf), [요구사항 참조](./RAG_프로젝트_요구사항_참조.md), [구현목표 정의서](./구현목표_정의서.md)
- 우선순위: 원본 필수 요구사항 → 사용자와 합의한 서비스 방향 → 이 문서의 구현 제안.
- 기존 구현목표 정의서의 ‘도메인 미정’ 상태를 변경하지 않고, 이 문서에서 집.착 후보의 구체적인 설계를 제안한다.
- 원본의 대외비 표시와 이용 범위를 존중해 내부 기획·개발 참조용으로 관리한다.

## 1. 서비스 개요

집.착은 직장 위치와 예산, 주택 유형, 공원 접근성, 선호 연령 구성, 따릉이 접근성 등을 기준으로 살기 좋은 동네와 주거 후보를 탐색하는 지도·대화형 서비스다.

사용자는 지도에서 지표별 분포와 개인 적합도를 확인하고, 추천 순위가 표시된 핀을 선택한다. 부동산 상세를 선택한 시점에 해당 위치에서 직장까지 대중교통·도보·자전거 경로를 조회한다. 사이드 챗봇과 대화를 이어가며 조건을 수정하고, 추천 이유와 지역 간 차이를 출처와 함께 확인한다.

실거래 자료로 탐색 가능한 가격대를 보여주며, 현재 계약 가능한 매물의 존재나 입주 가능 여부를 보장하지 않는다. 서비스의 적합도는 사용자 선호에 따른 자체 계산값으로, 공식 평가나 투자 수익 예측이 아니다.

## 2. 해결할 문제와 대상 사용자

### 2.1 문제

- 가격, 지역 인구, 공원, 따릉이, 출퇴근 경로를 여러 서비스에서 각각 확인해야 한다.
- 같은 지역이라도 사용자 예산·직장·생활 방식에 따라 적합성이 달라진다.
- 추천 결과가 어떤 데이터와 기준에서 나왔는지 이해하기 어렵다.
- 대화 중 조건을 바꿀 때 검색을 처음부터 반복해야 한다.

### 2.2 핵심 사용자

- 직장 위치가 정해져 있고 예산 안에서 이사할 지역을 찾는 직장인.
- 소형 전월세, 오피스텔, 연립다세대 등을 찾는 1인 가구.
- 공원·따릉이 접근성처럼 개인 생활 기준을 중요하게 여기는 사용자.

연령 구성은 사용자가 선택한 생활환경 선호를 설명하는 통계로 사용한다. 특정 연령·성별 주민 비율을 안전성이나 지역의 우열로 단정하지 않는다. 개인의 성별 입력은 필수 조건으로 받지 않는다.

## 4. 범위와 도메인 확정 조건

### 4.1 RAG의 기본 항목

**기본 항목은 ‘서울의 동네’로 정의한다.** 명칭과 법정동 코드가 있는 항목을 100개 이상 확보하고, 행정동 통계와 연결한다. 부동산 건물·단지·거래 기록은 동네에 연결되는 상세 데이터다.

이 구분은 ‘동네 설명 문서’가 건물 자체의 설명 문서인 것처럼 취급되는 문제를 피하기 위한 설계다. 지도에서 건물을 누르면 상위 동네를 RAG 선택 항목으로 연결하고, 건물 식별 정보와 최신 조회 결과를 상세 맥락으로 추가한다. UI에 현재 상담 중인 동네와 선택한 건물을 모두 표시한다.

동네 단위 선택·채팅 기록 분리와 항목별 외부 설명 문서 확보를 F2001~F2009의 기준으로 삼는다. 건물별 특성은 확인 가능한 건물 자료가 있을 때만 설명한다.

### 4.2 도메인 확정 전 증명할 조건

1. 동네 ID·명칭·속성을 가진 메타데이터 100건 이상을 실제로 확보한다.
2. 각 동네 자체를 설명하는 공식 소개 페이지·공개 자료·문서의 본문과 원문 출처를 연결한다. 지자체 동 소개·지역 현황 자료를 우선 조사한다.
3. 동네 자체 문서를 확보하지 못한 항목은 데이터셋 준비 완료로 세지 않는다. 검색 실패를 자체 생성 소개문으로 대체하고 외부 문서라고 표시하지 않는다.
4. 샘플 동네 10개에서 지역 코드 연결, 좌표·거래 매칭, 외부 문서 검색·본문 수집을 먼저 검증한다.
5. 아래의 근거가 필요한 질문 3개 이상에 대해 실제 출처를 확보한다.

대표 질문:

- “이 동네에서 최근 6개월, 전용 20~40㎡ 오피스텔의 월세 계약 분포는 어때? 보증금 조건도 나눠줘.”
- “또래 주민 비율이 높다는 근거가 뭐야? 기준 연월과 비교 지역도 알려줘.”
- “A동네와 B동네 중 공원과 따릉이 접근성이 내 조건에 더 맞는 곳은 어디야?”
- “이 건물에서 직장까지 40분 안에 갈 수 있어? 실제 경로가 확인됐어?”

원본의 도메인 확정 시한은 **1일차 16시**다. 실제 달력 날짜는 교육 일정에 맞춰 기록한다. 시한까지 확보 조건을 충족하지 못하면 원본에 따라 제공 영화 도메인 팩으로 전환한다.

## 5. 사용자 시나리오

### 5.1 첫 탐색

1. 사용자가 직장 주소를 검색하고 지도에서 위치를 확인한다.
2. 거래 유형·보증금·월세 또는 매매 예산·면적·주택 유형을 입력한다.
3. 공원·희망 연령대 구성·따릉이 접근성 등의 중요도를 조정한다.
4. 직장 주변 탐색 범위 안에서 예산 등 필수 조건을 충족하는 주거 후보를 찾는다.
5. 개인 적합도를 계산하고 동네 색상과 건물 추천 순위 핀을 표시한다.
6. 건물 선택 시 경로를 조회하고 가격 분포·추천 이유·근거·기준일을 보여준다.

초기 탐색 범위는 직장 기준 반경 또는 선택 지역으로 설정한다. 이는 실제 통근 가능 영역이 아니다. 실제 경로시간을 조회하지 않은 초기 순위에는 ‘통근시간 검증 전’을 표시한다.

### 5.2 챗봇 탐색

입력 예시:

> 보증금 1천만 원, 월세 70만 원 이내의 소형 주거를 찾아줘. 또래가 많은 동네이고 공원과 따릉이 대여소가 가까우면 좋겠어.

직장·면적 범위·또래의 연령 범위 등 필수 정보가 없으면 필요한 항목만 확인한다. 조건 칩과 추천 지도를 갱신하고, 순위별 이유와 확인되지 않은 내용을 안내한다.

후속 입력 예시:

> 월세는 80만 원까지 괜찮아. 공원보다 따릉이를 더 중요하게 해줘.

월세 상한과 중요도만 수정하고 직장·보증금·면적 등 기존 조건은 유지한다. 변경 전후 조건을 화면에서 확인할 수 있게 한다.

### 5.3 통근 상한을 대화에서 요구한 경우

‘40분 이내’처럼 실제 통근시간 조건을 요구하면 최초 후보에는 미검증 상태를 표시한다. 사용자가 선택한 후보부터 경로를 조회하며, 시간 미확인 후보를 ‘40분 이내 확정’으로 추천하지 않는다.

여러 후보의 자동 통근 검증은 추가 조회 기능으로 제공하되 호출량 상한·비용·약관을 확인한 뒤 활성화한다. 조회한 후보만 시간 조건을 확정 적용하고 재정렬한다. 사용자 동의 없이 시간·예산 조건을 완화하지 않는다.

### 6.1 지도 레이어

- 개인 적합도: 정규화한 사용자 선호 점수를 동네 색상으로 표시.
- 가격: 거래 유형·면적·보증금 구간이 같은 표본의 가격 요약.
- 공원 접근성: 실제 보유한 좌표·입구 자료의 수준에 맞춰 거리 표시.
- 연령 구성: 사용자가 지정한 연령 범위의 주민 비율.
- 따릉이: 대여소 핀과 가까운 대여소까지의 직선거리.
- 현재 환경: 미세먼지·혼잡도. 장기 주거 적합도와 구분한 보조 레이어.

초기에는 동네 경계의 단계별 색상 또는 데이터 지점 도트를 사용한다. 연속 그래디언트는 보간 방법과 공간 해상도를 설명할 수 있을 때 추가한다. 데이터 없는 곳은 회색이며 낮은 점수로 간주하지 않는다.

### 7.1 데이터 해석 원칙

- 실거래가는 신고된 과거 계약 자료이며 호가·현재 매물·입주 가능성을 뜻하지 않는다.
- 원룸은 면적만으로 확정하지 않는다. 구조가 미확인인 경우 ‘소형 주거’로 표현한다.
- 전원주택은 실제 등록 유형에 맞춰 단독주택 등으로 연결하며 독립된 API 필터가 확보됐다고 가정하지 않는다.
- 월세는 보증금 구간을 함께 비교한다. 보증금이 다른 거래의 월세를 단순 평균해 저렴하다고 판단하지 않는다.
- 단독·다가구 건물 전체 매매와 개별 임대 공간의 면적·가격을 혼합하지 않는다.
- 가격 집계에는 기간·유형·면적·표본 수·최신 거래일을 표시한다. 초기 제안인 표본 5건 미만은 ‘거래 표본 부족’으로 표시하며 기준은 설정화한다.
- 거래 취소·정정·중복을 반영한다. 정확한 필드가 없으면 처리 한계를 기록한다.
- 동네의 연령 비율은 구매자 나이와 다르며 주민등록 인구는 실제 체류 인구와 다르다.
- 법정동·행정동 코드와 기준 경계를 구분한다. 다대다 대응을 임의의 1:1로 바꾸거나 같은 통계를 여러 동에 중복 합산하지 않는다.
- 세부 동네로 통계를 정확히 배분할 수 없으면 원래 행정동 범위를 표시한다.

## 8. 개인 적합도와 추천 순위

### 8.1 필수 조건과 선호 분리

필수 조건은 거래 유형, 예산 상한, 면적·주택 유형, 탐색 범위다. 공원·연령 구성·따릉이는 기본적으로 가중 선호이며 사용자가 ‘반드시’라고 지정하면 검증 가능한 필수 조건으로 전환한다.

예산에 맞는 최근 거래가 있었다는 조건과 현재 해당 가격의 매물이 있다는 조건을 구분한다. 현재 매물 데이터가 없는 상태에서 후자는 충족했다고 답하지 않는다.

### 8.2 점수 계산 제안

각 지표를 0~1로 정규화하고 사용자 가중치의 합을 1로 만든 뒤 `적합도 = 100 × Σ(가중치 × 지표점수)`로 계산한다. 초기 예시 가중치는 예산 0.4, 공원 0.25, 희망 연령 구성 0.2, 따릉이 접근성 0.15다. 이는 공식 지수가 아닌 조정 가능한 시작값이다.

- 예산 점수: 동일 조건의 최근 거래 분포와 사용자 상한 간 여유를 사전 정의한 규칙으로 계산.
- 공원 점수: 후보 위치에서 가까운 공원까지의 거리에 따른 감소 함수. 입구·경로가 없으면 직선거리임을 표시.
- 연령 점수: 지정 연령 인구 비율을 고정된 비교 범위·기준 시점에서 정규화.
- 따릉이 점수: 가까운 대여소까지의 거리와 주변 대체 대여소 접근성.

거리 기준·정규화 범위·동률 정렬 규칙은 설정에 둔다. 지도 확대·축소만으로 같은 후보의 점수가 바뀌지 않도록 정규화 기준을 고정한다. 결측 지표를 0점으로 넣지 않고 ‘미확인’으로 처리한다. 핵심 선호가 미확인인 후보는 확정 순위와 분리해 표시한다.

### 8.3 지도와 핀의 단위

- 동네 색상: 해당 동네의 지표 또는 필터를 통과한 건물 점수의 중앙값 등 명시한 집계값.
- 숫자 핀: 위치가 확인된 건물·단지 후보의 순위. 표시하는 후보 범위와 전체 후보 수를 함께 안내.
- 단독·다가구 위치 미확정 거래: 동네 집계로만 표시하고 개별 집처럼 핀을 찍지 않음.
- 초기 순위에는 실제 경로시간을 반영하지 않음. 직장 위치는 탐색 범위 설정에 사용.
- 경로 검증 후 순위를 바꿀 경우 ‘통근 확인 후보 순위’를 따로 표시하고 변경 이유를 안내.

## 9. 부동산 선택 시 경로와 따릉이

건물 좌표와 직장 좌표가 확인된 경우에만 경로 API를 호출한다. 대중교통·도보·자전거의 결과를 독립적으로 처리해 한 수단의 실패가 다른 결과를 가리지 않게 한다.

- 대중교통: 총 예상시간, 도보·환승 등 제공되는 세부 정보, 조회 시각.
- 도보: 보행 경로 기준 예상시간·거리.
- 개인 자전거: 자전거 경로 기준 예상시간·거리.
- 따릉이: 집→출발 대여소 도보 + 대여소 간 자전거 + 도착 대여소→직장 도보. 대여·반납 부가시간은 별도로 표시.

따릉이는 위치 정보만 사용한다. 현재·미래 자전거 재고, 예약 가능성, 반납 가능 여부를 추정하거나 보장하지 않는다. 가까운 대여소 후보는 좌표 거리로 추린 뒤 필요한 경우에만 상세 경로를 비교한다.

자전거 API 권한을 확보하지 못하면 ‘미지원/조회 불가’를 표시하고 지도 서비스의 외부 길찾기로 연결하는 대체안을 검토한다. 보행시간에 임의 비율을 곱한 값을 실제 자전거 API 결과로 표시하지 않는다. 기능 완성 판정에서는 미지원 상태를 미완료로 기록한다.

## 10. 데이터 저장과 두 Vector DB 컬렉션

### 10.1 구조화 저장소

거래 원자료, 건물·좌표, 동네 코드, 인구 통계, 공원·따릉이 위치는 관계형 또는 파일 기반 저장소로 관리한다. 예산 필터·수치 집계·공간 계산·경로 조회 결과는 코드로 처리한다. 모든 숫자를 임베딩 검색만으로 찾아 계산하지 않는다.

주요 엔터티: `neighborhoods`, `area_code_mapping`, `properties`, `transactions`, `population_stats`, `parks`, `bike_stations`, `source_documents`, `ingestion_cache`. 개인 세션의 직장·조건·대화는 공개 데이터와 분리한다.

### 10.2 컬렉션 A: `neighborhood_meta`

항목은 동네 1개이며 항목당 1개 검색 텍스트를 저장한다.

텍스트 예시 구조:

```text
동네명: {정식 명칭}
지역 코드: {법정동 코드 / 연결된 행정동 코드}
지역: {시·구·동}
주거 유형과 최근 거래 요약: {유형·기간·면적·표본 수를 포함한 검증값}
인구 구성: {희망 연령 비율 계산에 필요한 기준 통계와 기준일}
공원·따릉이 접근 특성: {공개 자료에서 확인된 내용}
출처와 기준일: {각 데이터의 출처·시점}
```

임베딩 ID는 `neighborhood:{법정동코드}`로 고정해 upsert한다. 메타데이터에는 항목 ID·명칭·출처·기준일·스냅샷 버전을 저장한다. 최신 거래·경로 결과는 조회 시 별도로 검증하고 색인 요약과 시점을 구분한다.

### 10.3 컬렉션 B: `neighborhood_docs`

동네 자체 공식 소개와 공원·교통·지역 관련 외부 문서를 청킹해 저장한다.

필드: `item_id`, `item_name`, `document_id`, `title`, `source_type`, `source_url`, `page`, `retrieved_at`, `published_at`, `chunk_index`, `content_hash`, `snapshot_version`.

ID: `{item_id}:{document_id}:{chunk_index}`. 여러 동네가 같은 문서를 사용해도 덮어쓰지 않는다. PDF는 페이지를 추적하고 반복 머리말 등을 제거한다. HTML은 탐색 메뉴·광고 등 본문 외 영역을 제거한다.

초기 설정 제안은 청크 1,000자·중복 200자, 외부 근거 `k=6`, MMR `fetch_k=24`, `lambda_mult=0.5`다. 원본의 고정 요구값이 아니며 실험으로 조정한다. 선택 동네 메타데이터 1건은 외부 근거 수와 별도로 항상 포함한다.

## 11. 세 프롬프트와 RAG 파이프라인

### 11.1 외부 문서 준비

| 프롬프트 | 역할 | 입력 | 구조화 출력 제안 |
| --- | --- | --- | --- |
| P1 검색어 추출 | 주거·지역 정보 전문가 역할로 검색어 생성 | 선택 동네·질문·조건 | `item_id`, `queries`, `required_item_query` |
| P2 후보 선별 | 관련 있는 문서와 없는 문서 구분 | 후보 ID·제목·요약·출처·선택 동네 | `selected_ids`, `rejected_ids`, `reasons` |
| P3 답변 생성 | 근거와 확인된 수치만 사용해 추천 이유·비교 설명 | 질문·조건·근거 번호·확인된 조회 결과 | `answer`, `cited_ids`, `limitations` |

P1은 선택 동네 자체 검색어를 항상 포함한다. P2의 제외 규칙보다 동네 자체 문서 필수 포함 규칙이 우선한다. 선택한 항목과 무관한 문서를 이름이 비슷하다는 이유로 자체 문서로 인정하지 않는다.

외부 출처 검색은 허용된 공식 검색 API·공개 목록·문서 색인 경로를 출처별 어댑터로 구현한다. 로컬 Vector DB 검색만 하고 외부 수집을 완료했다고 처리하지 않는다. 정확한 외부 검색 경로와 실제 후보 수집은 착수 단계에서 검증할 조건이다.

검색어 추출 → 외부 후보 검색 → P2 선별 → 본문·출처 수집 → 청킹·임베딩 → 컬렉션 B 적재 순서를 구현한다. 캐시 키는 출처·동네 ID·정규화 검색어·수집 정책 버전으로 구성하고, 완료 상태인 검색어는 다시 수집하지 않는다. 실패 상태는 정상 수집 완료와 구분한다.

### 11.2 조건 해석과 세 프롬프트의 관계

사용자 예산·선호를 JSON 조건으로 바꾸는 처리와 지도 액션 선택은 별도 애플리케이션 기능이다. 이를 필수 P1~P3의 대체물로 세지 않는다. 추가 프롬프트 또는 규칙 기반 파서를 사용할 수 있다.

조건 구조 예시: `workplace`, `search_area`, `deal_type`, `housing_types`, `deposit_max`, `rent_max`, `sale_max`, `area_range`, `preferred_age_range`, `weights`, `commute_limit`, `commute_mode`.

금액·단위·허용값을 검증하고 변경된 필드만 반영한다. 누락값을 추정해 필수 조건을 확정하지 않는다. 핀 좌표와 순위는 서버가 검증한 ID 목록으로 전달하며 LLM이 임의로 생성하지 않는다.

### 11.3 LangGraph

```text
데이터 준비·외부 수집·색인
              ↓
사용자 질문 → 조건 해석·필터·추천 계산 → 선택 동네와 확인된 데이터
              ↓
START → retrieve → generate → END
          │            │
          │            └─ P3: 근거 기반 답변과 실제 인용 ID
          └─ 선택 동네 메타데이터 항상 포함
             + 외부 문서 유사도 또는 MMR 검색
             → 병합·중복 제거·근거 번호 부여
              ↓
답변·인용 근거 표시 + 검증된 지도 액션
```

검색은 선택 동네 ID로 범위를 제한한다. 비교 질문은 비교 대상 ID 각각의 메타데이터를 포함하고 대상 집합에 관련된 문서를 검색한다. 범위가 다른 문서가 섞이면 제외한다. 문서 버전·청크 ID·본문 해시를 활용해 중복을 제거하고 실제 최종 근거 수를 기록한다.

최신 API 응답·계산 결과는 출처·조회 시각·계산 기준을 가진 구조화 근거로 추가한다. 이것만으로 두 컬렉션 검색을 대체하지 않는다. 고정된 RAG 문서와 최신 조회 결과가 충돌하면 시점 차이를 표시하고 해결되지 않은 내용을 단정하지 않는다.

주요 주장에 근거 번호를 붙이고 실제 인용된 문서만 제목·원문 URL 또는 파일명·쪽과 함께 표시한다. 존재하지 않는 인용 ID는 거부한다. 인용이 없으면 ‘이 답변에 인용된 근거가 없습니다’를 표시한다. 출처 유형은 항목 메타데이터·외부 문서·최신 조회/계산으로 구분한다.

문서가 없으면 확인 불가를 답한다. 자료 부족으로 추정한 통근시간·치안·투자 수익·전세 안전성 등을 만들어내지 않는다. 외부 문서의 지시문은 데이터로 취급하고 시스템 동작 지시로 실행하지 않는다.

## 12. 대화 상태와 지도 동기화

전역 탐색 대화와 동네별 상담 기록을 분리한다. `item_id`별 대화 기록을 유지하고 동네 전환 시 해당 기록만 표시한다. 같은 동네의 다른 건물을 선택하면 건물 맥락 변경을 표시한다.

서버 응답은 `answer`, `citations`, `conditions`, `condition_revision`, `candidate_ids`, `selected_item_id`, `map_action`, `warnings` 등으로 구성하는 것을 제안한다. 상세 경로에는 `property_id`, `origin`, `destination`, `mode`, `queried_at`, `duration`, `status`를 포함한다.

조건·직장·선택 건물이 바뀌면 이전 요청의 늦은 응답으로 지도가 덮어써지지 않도록 revision을 검증한다. 출발 위치가 확인되지 않은 경우 다른 건물 좌표를 대신 사용하지 않는다.

## 13. 기술 구성과 운영 원칙

Python 3.10+, Streamlit UI, LangChain·LangGraph, ChromaDB를 기본으로 한다. 원본 5~6쪽의 지정 라이브러리 버전을 우선 확인하고 설치·호환성을 검증한다. 지도 SDK, 주소 변환, 경로 제공업체는 별도 확정한다.

권장 모듈: `domain/` 데이터·코드 정규화, `collectors/` 외부 수집, `indexing/` 청킹·색인, `retrieval/` 유사도·MMR, `rag/` 그래프·프롬프트, `recommendation/` 필터·점수, `routing/` 경로, `ui/` 지도·채팅, `evaluation/` 평가·도표.

추천·지도 계산과 LLM 답변을 분리해 먼저 후보를 표시하고 설명은 진행 상태와 함께 갱신한다. 거래 API는 시군구·연월 단위로 조회해 후보가 공유하는 결과를 재사용한다. 최신성 요구와 제공자 이용 조건에 맞춰 만료·갱신 정책을 설정한다. 외부 문서 수집 캐시와 실시간 조회 캐시는 별도로 관리한다.

키는 환경변수에서 읽고 소스·사용자 화면·실험 로그에 포함하지 않는다. 서버용 키를 지도 HTML에 넣지 않는다. 공개용 지도 키는 제공자 방식대로 도메인 제한을 적용한다. 직장 위치·예산·대화는 기본 세션 범위에서 처리하고 평가 로그는 가상 프로필로 작성한다.

화면에 키·전체 프롬프트·오류 추적을 노출하지 않는다. 오류는 사용자용 요약과 내부 진단으로 구분한다. 타임아웃·재시도·호출 간격·User-Agent·출처 표시·저장 제한을 제공자별로 적용한다.

부동산 계약·재무 판단과 연결되므로 ‘공개 자료 기반 탐색 정보이며 공인중개·법률·금융 전문가의 검토를 대신하지 않는다’는 안내를 제공한다. 단순한 주거 추천을 계약 안전성 보장으로 표현하지 않는다.

## 14. 비교 실험과 정량 검증

### 14.1 실험 조건

| 조건 | 구성 | 비교 목적 |
| --- | --- | --- |
| A | RAG 미사용, 동일 모델·질문·사용자 조건 | 근거 검색 없이 생성한 답변 기준선 |
| B | RAG + 유사도 검색 | 근거 제공 효과 |
| C | RAG + MMR 검색 | 근거 다양성·품질·검색 비용 차이 |

비교의 원인을 분리하기 위해 구조화 데이터 조회 결과·추천 계산값은 A/B/C에 동일하게 제공하는 주 실험을 권장한다. A에는 Vector DB 메타데이터·외부 문서 근거를 주지 않는다. 이 실험은 ‘전체 API 사용 효과’가 아니라 ‘문서 RAG 추가 효과’를 평가한다. 이 정의는 기존 구현목표의 조건을 집.착에 맞게 구체화한 것이다.

완전한 무자료 LLM과 비교하는 실험을 추가하면 별도 실험으로 기록하며 주 실험과 합산하지 않는다. A에도 근거가 없는 사항을 모른다고 답할 수 있게 하고 없는 인용을 강제하지 않는다.

B/C는 같은 문서 스냅샷·임베딩 모델·선택 항목·필터·청킹·최종 외부 근거 수·생성 설정을 사용한다. 최종 근거 수와 토큰 수를 기록한다. 경로·현재 환경은 고정 응답 스냅샷으로 통제하고, 실시간 연동 성능은 별도로 측정한다.

### 14.2 평가 세트

원본 F2015 최소 5개 이상을 충족하며 프로젝트 목표로 20~30개 질문·조건별 3회 반복을 제안한다. 실제 규모는 비용에 따라 확정한다. 개발용과 최종 평가용 질문을 분리하고 정답·출처·판정 규칙을 실행 전에 고정한다.

질문 유형: 가격 조건, 지역 통계 해석, 공식 시설 설명, 지역 비교, 근거 없는 질문, 통근 미검증 조건, 다중 대화 조건 변경. 문서 내용이 필요한 질문을 충분히 포함해 API 수치만으로 답하는 평가로 치우치지 않게 한다.

### 14.3 지표

| 지표 | 계산·판정 기준 |
| --- | --- |
| 사실 정확성 | 사전 정의한 필수 사실 요소 중 정확히 답한 수 / 필수 사실 요소 수 |

분모가 0이면 N/A로 표시한다. A의 문서 검색·검색 인용 지표는 N/A로 구분한다. 무응답으로 정확성이 부풀려지지 않도록 응답 성공률을 같이 보고한다. MMR이 반드시 개선된다고 전제하지 않는다.

### 14.4 기록과 시각화

질문·항목·조건·모델·프롬프트·데이터 버전, 검색 설정, 원문 ID·청크 ID, 답변·인용·평가, 캐시 상태, 실행 시각과 단계별 시간을 저장한다. 성능은 평균·중앙값·표준편차와 표본이 충분하면 p95를 제시한다. 반복 실행 수와 서로 다른 질문 수를 구분한다.

산출물은 조건별 품질 막대그래프, 검색·생성 시간 구성도, 응답시간 분포, 근거 적합도·다양성 표, 같은 질문의 A/B/C 답변 비교표, 실패 사례 분석이다. 모든 도표에 단위·질문 수·실행 수·실험 조건을 표시한다.

최초 수집·색인 시간과 준비 완료 질의 시간을 분리한다. 경로 조회는 부동산 클릭 후 별도 측정한다. 반응 시간의 목표 초는 제공업체 실측 후 확정하며, 임의의 숫자를 달성했다고 기재하지 않는다.
