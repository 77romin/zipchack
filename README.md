# 집.착

> **내 맘에 착, 내 삶에 착.**
> 예산부터 출근길까지, 나에게 착 맞는 집과 동네.

집.착은 사용자의 직장 위치와 예산, 생활 취향을 바탕으로 동네와 주거 후보를 추천하는 지도·대화형 웹앱을 목표로 합니다. 이름에는 집을 꼼꼼하게 따져본다는 의미와, 내 마음에 ‘착’ 맞는 집을 찾는다는 의미를 담았습니다.

현재는 초기 기능 구현 단계입니다. 구현 완료 범위와 실행법은 [실행 가이드](./docs/실행가이드.md), 변경 이유는 [개발일지](./docs/개발일지.md)를 참고하세요. 아래의 전체 서비스 설명에는 후속 구현 계획도 포함됩니다. 이 문서는 프로젝트를 시작한 이유와 만들고 싶은 사용 경험, 구현 방향을 소개합니다. 실거래가 기반 주거 추천·RAG는 후속 구현이며, 도시데이터의 인증키 실조회와 실제 지도 브라우저 검증은 별도로 확인해야 합니다.

## 왜 만들게 되었나

집을 고르는 일은 앞으로의 일상을 고르는 일이기도 합니다. 매일 얼마나 출근해야 하는지, 퇴근 후 걸을 공원이 있는지, 자전거를 이용하기 편한지에 따라 같은 가격의 집에서도 생활은 달라질 수 있습니다.

우리가 해결하고 싶은 문제는 이런 조건을 한곳에서 비교하기 어렵다는 점입니다. 가격을 찾아보고, 지도에서 공원을 확인하고, 직장까지 길찾기를 해본 뒤 다른 후보에서 같은 과정을 반복해야 합니다. 마음에 드는 조건을 하나 추가하면 다시 비교해야 합니다.

집.착은 여기서 출발했습니다.

> **“내 예산과 생활 방식에 맞는 곳을 지도에서 찾고, 왜 나에게 맞는지도 물어볼 수 없을까?”**

누군가에게는 짧은 출근길이, 다른 누군가에게는 가까운 공원과 따릉이 대여소가 중요합니다. 집.착은 사용자가 중요하게 생각하는 조건을 추천 기준으로 삼고, 그 결과를 이해할 수 있게 만들고자 합니다.

## 어떤 경험을 만들고 싶은가

처음에는 직장 위치와 감당할 수 있는 가격대를 입력합니다. 원하는 주택 유형과 면적을 고르고, 공원·희망 연령대 구성·따릉이 접근성 등의 중요도를 정합니다.

지도는 이 조건에 따라 달라집니다. 가격이나 연령 구성 같은 개별 지표를 색으로 살펴볼 수도 있고, 여러 조건을 합친 개인 적합도를 볼 수도 있습니다. 위치가 확인된 주거 후보에는 추천 순위를 숫자 핀으로 표시합니다.

관심 있는 부동산을 누르면 출발지와 직장을 지정한 카카오맵 대중교통·도보·자전거 길찾기 화면으로 연결하는 것을 계획합니다. 제휴 API는 사용하지 않으며 이동시간을 집.착 안으로 자동 수신하지 않습니다. 상세 정보를 살펴본 뒤에는 옆의 챗봇에 질문할 수 있습니다.

> “보증금 1천만 원, 월세 70만 원 이내로 찾아줘. 또래가 많은 동네에 공원도 가까웠으면 좋겠어.”
>
> “월세는 80만 원까지 괜찮아. 공원보다 따릉이를 더 중요하게 해줘.”
>
> “이 동네가 다른 곳보다 추천 순위가 높은 이유가 뭐야?”

챗봇은 기존 조건을 기억하면서 바뀐 조건만 반영하고, 지도와 추천 결과를 함께 갱신합니다. 답변에는 추천 이유를 뒷받침하는 자료와 기준 시점을 표시합니다. 정보가 부족한 부분은 확인되지 않았다고 안내합니다.

## 무엇을 기준으로 추천할 것인가

| 기준 | 살펴볼 내용 | 사용 방식 |
| --- | --- | --- |
| 예산 | 매매가 또는 보증금·월세, 면적별 최근 거래 | 상한 등 필수 조건으로 후보 필터링 |
| 공원 | 주변 공원 위치와 접근 거리 | 사용자가 정한 중요도에 반영 |
| 인구 구성 | 사용자가 지정한 연령대의 주민 비율 | 동네 특성을 설명하는 참고 지표 |
| 따릉이 | 집과 직장 주변 대여소 위치 | 대여소 접근성에 반영 |
| 통근 | 관심 주거지에서 직장까지 이동시간 | 후보 선택 후 외부 카카오맵에서 확인 |
| 미세먼지·혼잡도 | 제공 범위 내 현재 관측·혼잡 정보와 통합대기환경지수 | 장기 주거 조건과 구분한 보조 레이어 |
| 주차·전기차 | 주차장 위치·요금·실시간 제공 여부, 충전소 위치·운영·제한 | 시설 레이어와 명시적 사용자 선호 비교 |
| 지하철 | 역·호선·주소·위치 | 시설 레이어와 역·노선 수 비교. 통근시간과 구분 |
| 현재 인구 구성 | 성별·연령별 실시간 비율 | 구성 차트. 선택 연령대는 현재환경 비교에만 사용 |
| 상권 | 장소·업종 현황, 신한카드 결제 범위·소비 구성 | 활동 선호 비교. 전체 매출·거주민·소음과 구분 |

예산처럼 반드시 지켜야 하는 조건과 공원처럼 우선순위를 줄 수 있는 선호를 구분합니다. 필수 조건을 충족하는 후보에 대해 지표를 정규화하고 사용자 가중치를 적용해 점수를 계산합니다. 추천 이유에는 어떤 기준이 점수에 영향을 주었는지도 보여줍니다.

초기 순위에는 아직 조회하지 않은 실제 통근시간을 반영하지 않습니다. 통근 상한을 요구한 경우에는 시간 미확인 후보와 경로 검증을 마친 후보를 구분합니다. 조건에 맞는 결과가 없으면 임의로 예산이나 시간을 늘리지 않고 변경 가능한 조건을 제안합니다.

## 어떤 데이터를 사용할 것인가

부동산은 국토교통부의 주택 유형별 실거래 자료, 인구 구성은 행정안전부·SGIS 통계, 따릉이는 서울시 대여소 위치 자료를 활용하는 방향입니다. 공원과 동네 설명은 지자체 공식 자료를 연결하고, 현재 환경·시설·상권은 서울 실시간 도시데이터를 주 공급처로 사용하고, 제공 범위 밖의 환경 정보가 필요하면 에어코리아 등 별도 자료를 검토합니다.

지도·주소 검색은 카카오맵을 사용합니다. 제휴 API를 사용하지 않는 조건에 따라 경로 확인은 [카카오맵 공식 길찾기 바로가기](https://apis.map.kakao.com/web/guide/#routeurl)로 연결할 계획입니다. 일반 지도 API에 이동시간 응답 기능이 포함된 것으로 간주하지 않습니다.

따릉이는 **대여소 위치와 접근성만** 사용합니다. 초기 범위에 실시간 자전거 재고나 예약 기능은 포함하지 않습니다. 따릉이 통근을 확인할 때는 집에서 대여소까지의 도보, 대여소 사이의 자전거 이동, 직장까지의 도보를 나누어 살펴봅니다.

주택 유형은 아파트·연립다세대·오피스텔을 우선 검토하고, 단독·다가구도 공개 범위에 맞춰 연결합니다. 정확한 건물을 특정하기 어려운 자료는 동네별 거래 분포로 보여줍니다. ‘원룸’이나 ‘전원주택’이라는 생활상의 표현을 실제 데이터 분류와 연결하는 과정도 필요합니다.

공식 출처별 링크와 미확정 사항은 [서비스 기획서의 데이터 및 API 계획](./docs/집착_서비스_기획서.md#7-데이터-및-api-계획)에 정리했습니다.

## 서울 도시데이터로 생활환경 살펴보기

[서울 실시간 도시데이터 공식 명세](https://data.seoul.go.kr/dataList/openApiView.do?infId=OA-21285&srvType=A)를 기반으로 다음 기능을 구현했습니다. 서울 키는 기존 `SEOUL_OPEN_DATA_API_KEY`를 그대로 사용합니다.

| 화면 | 제공하는 정보 | 해석 기준 |

| 인구 구성 | 남성·여성·연령별 비율, 상주 비율, 혼잡도·인구 범위 | 현재 추정 인구. 거주민만의 구성과 다름 |
| 주차장 | 이름·주소·수용 면수·요금·주차 가능 면수·기준 시각 | 실시간 제공이 Y인 값만 가능 면수로 표시 |
| 지하철 | 역명·호선·주소·좌표 | 동일 역의 여러 노선은 구분, 경로시간 미제공 |
| 전기차 충전 | 충전소 위치·운영시간·제한, 충전기별 타입·상태 코드·출력·시각 | 존재와 즉시 이용 가능성을 구분 |
| 대기환경 | 통합대기환경등급·지수·결정물질, PM10·PM2.5 | 장소 단위 현재값, 건물별 관측·장기 평균과 다름 |
| 상권 | 장소·업종 현황, 결제 건수·금액 범위·가맹점 수·소비 구성 | 신한카드 내국인 표본, 전체 매출·인구 구성과 다름 |

주차장·지하철·충전소는 지도에서 레이어를 켜고 끌 수 있습니다. 유효 좌표가 있는 시설만 표시하고, 직장을 선택했다면 탐색 반경 안으로 한정합니다. 조회 장소가 직장이나 주거 후보와 자동 연결됐다고 가정하지 않습니다.

현재환경 비교에서는 주차장·역/노선·이용제한 없음 충전소·대기환경·상권 활동·현재 인구 연령대에 중요도 0~5를 설정할 수 있습니다. 조회한 장소를 최대 10곳까지 세션의 비교 목록에 추가하고, 같은 장소를 다시 추가하면 최신 조회 결과로 갱신합니다. 성별 구성은 정보로 보여주고 순위나 안전성 점수에 사용하지 않습니다.

점수는 확인된 지표의 가중 평균입니다. 지표가 빠지면 0으로 채우지 않고 충족률과 참고점수를 표시하며 확정 순위는 부여하지 않습니다. 계산 규칙은 화면에 공개합니다. 이 점수는 **현재환경 비교용**이며 예산·건물 특성까지 포함한 주거 추천 순위와는 별개입니다. 상권 활동이 적다는 것이 소음이 적다는 뜻도 아닙니다.

서울시 제공 장소만 조회할 수 있으며 서울 전역을 촘촘하게 관측하는 자료가 아닙니다. 장기 이력 수집 대신 사용자가 조회한 결과만 세션에서 유지합니다. 자료가 없는 곳은 미제공으로 남기고 가짜 데이터를 서비스 결과로 대체하지 않습니다.

## 왜 RAG를 사용하는가

“이곳이 당신에게 맞습니다”라는 문장만으로는 사용자가 추천을 판단하기 어렵습니다. 어떤 가격 자료와 지역 통계를 사용했는지, 주변 시설의 특징이 무엇인지, 무엇이 아직 확인되지 않았는지 설명할 수 있어야 합니다.

집.착에서 RAG는 **추천 이유를 자료에 근거해 설명하고, 사용자의 후속 질문에 답하는 역할**을 맡습니다. 가격 계산과 거리 계산, 필터링은 코드로 처리하고, LLM은 확인된 수치와 검색한 문서로 설명을 구성합니다.

지도와 추천 점수를 계산하는 기능만으로 RAG를 구현했다고 보지 않습니다. 실제로 외부 문서를 수집·청킹·임베딩하고 검색하는 흐름을 별도로 만듭니다.

## 어떻게 만들 것인가

### 1. 동네와 주거 데이터를 준비한다

서울의 동네 100개 이상을 RAG의 기본 항목으로 준비하는 것을 목표로 합니다. 각 동네에는 이름·지역 코드·주거 및 인구 특성을 연결하고, 해당 동네 자체를 설명하는 외부 문서를 확보합니다. 건물과 거래 기록은 동네에 연결되는 상세 데이터로 관리합니다.

먼저 동네 10개로 거래·통계·좌표·설명 문서를 실제 연결할 수 있는지 확인하고 범위를 확장합니다. 법정동과 행정동의 차이, 자료별 기준 시점, 위치가 비공개인 거래 등을 확인하는 작업을 우선합니다.

### 2. 두 개의 벡터 컬렉션을 만든다

| 컬렉션 | 저장 내용 | 역할 |
| --- | --- | --- |
| 동네 메타데이터 | 동네 1개를 하나의 검색 텍스트로 구성한 정보 | 조건에 맞는 동네 탐색과 기본 근거 |
| 외부 문서 | 동네 소개·공원·교통시설 등의 문서를 청킹한 정보 | 추천 이유와 지역 비교의 설명 근거 |

청크에는 문서 제목·원문 출처·관련 동네·수집 시점을 저장합니다. 고정된 식별자로 중복 색인을 방지하고 청크 크기·중복 길이·검색 근거 수는 설정으로 바꿀 수 있게 합니다.

### 3. 세 프롬프트로 수집과 답변을 연결한다

1. **검색어 추출:** 선택한 동네와 사용자 질문에서 외부 문서 검색어를 추출합니다.
2. **후보 선별:** 외부 검색 결과에서 관련 문서를 고르고 본문과 출처를 수집합니다.
3. **답변 생성:** 검색한 근거를 바탕으로 답변하고 주요 주장에 근거 번호를 표시합니다.

선택한 동네 자체를 설명하는 문서는 검색·색인 대상에 반드시 포함합니다. 이미 수집·색인한 검색어는 캐시해 불필요한 재수집을 줄입니다. 사용자 조건 해석과 지도 갱신은 이 세 프롬프트를 보완하는 애플리케이션 기능으로 구현합니다.

### 4. LangGraph로 검색과 생성을 분리한다

LangGraph는 `retrieve → generate` 흐름으로 구성합니다. 검색 노드는 선택한 동네 메타데이터와 관련 외부 문서를 모아 중복을 제거하고, 생성 노드는 그 근거로 답변합니다.

최신 가격 등 실제 조회·계산한 값만 기준 시점과 함께 근거로 전달합니다. 외부 카카오맵에서 확인한 이동시간은 앱이 자동 확보한 근거로 처리하지 않습니다. 화면에는 실제로 인용한 자료만 제목과 원문 출처로 표시하고, 근거가 없으면 확인할 수 없다고 답합니다.

### 5. 지도와 대화를 연결한다

Python과 Streamlit을 기반으로 지도·조건 패널·상세 패널·챗봇을 구성하는 것을 초기 구현안으로 둡니다. 벡터 저장소에는 ChromaDB를 사용하고, 수집·색인·검색·생성·추천·경로·UI의 책임을 나눕니다.

조건이 바뀌면 서버가 후보와 순위를 다시 계산해 지도에 전달합니다. 챗봇이 임의로 건물 좌표나 순위를 만들게 하지 않습니다. 선택한 동네별 대화 기록을 유지하고, 길찾기는 관심 후보를 클릭한 뒤 카카오맵으로 연결해 확인하도록 설계합니다.

## 무엇으로 결과를 검증할 것인가

이 프로젝트는 동작하는 화면과 함께, RAG가 답변에 어떤 차이를 만드는지 측정하는 것을 목표로 합니다.

| 비교 조건 | 확인할 내용 |
| --- | --- |
| RAG 미사용 | 문서 검색 없이 생성한 답변의 기준 성능 |
| RAG + 유사도 검색 | 질문과 유사한 근거를 제공했을 때의 변화 |
| RAG + MMR 검색 | 관련성과 다양성을 함께 고려했을 때의 변화 |

주 실험에서는 같은 모델·질문·사용자 조건과 동일한 구조화 조회 결과를 사용하고, 문서 검색의 유무·방식을 달리합니다. 품질은 사실·수치 정확성, 근거 일치, 모르는 질문에 대한 적절한 유보로 평가합니다. 서비스 측면에서는 조건 위반 추천, 대화 중 조건 유지, 지도와 답변의 일치도 확인합니다.

검색·생성·전체 응답시간과 실패율을 측정하고, 최초 수집·색인 비용 및 클릭 후 길찾기 연결 동작은 별도로 검증합니다. 외부 지도에서 계산한 시간은 앱의 API 응답시간으로 측정하지 않습니다. 대표 질문은 요구사항의 최소 5개 이상을 충족하고, 20~30개 질문으로 확대하는 것을 목표로 합니다. 결과는 비교표와 도표로 정리하며 MMR이 항상 더 좋다고 가정하지 않습니다.

## 정보를 보여주는 원칙

- **가격의 의미를 명확히 합니다.** 최근 실거래는 현재 매물 가격이나 계약 가능 여부와 다릅니다.
- **데이터의 범위와 시점을 표시합니다.** 동네 통계나 인근 측정소 관측값을 개별 건물의 확정 정보처럼 표현하지 않습니다.
- **확인하지 못한 부분은 남겨둡니다.** 데이터가 없는 지역은 미확인으로 표시하고 임의로 점수를 채우지 않습니다.
- **추천 기준을 공개합니다.** 점수는 사용자의 조건과 서비스의 계산 규칙에서 나온 값임을 설명합니다.
- **사용자의 조건을 존중합니다.** 대화 중 요구하지 않은 조건을 바꾸거나 결과를 만들기 위해 상한을 완화하지 않습니다.
- **계약 판단의 한계를 알립니다.** 공개 자료 기반 탐색 정보이며 계약·법률·금융 전문가의 검토를 대신하지 않습니다.

## 첫 구현의 범위

서울을 중심으로 예산·공원·희망 연령 구성·따릉이 접근성에 따른 지도 추천과 근거 기반 상담을 먼저 구현합니다. 위치를 식별할 수 있는 주거 후보의 카카오맵 길찾기 화면 연결을 계획하고, 미세먼지·혼잡도는 제공 범위가 명확한 보조 레이어로 추가합니다.

단기임대 매물, 현재 매물의 실시간 재고, 투자 수익 예측, 따릉이 실시간 재고는 초기 범위에 포함하지 않습니다. 동네별 문서와 API 권한을 실제 확보한 결과에 따라 구현 범위를 확정합니다. 과제의 도메인 확정 조건과 미확보 시 대응은 상세 기획서를 따릅니다.
